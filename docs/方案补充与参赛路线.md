# 从校园服务平台到校园服务智能体

## 赛道定位

本项目按赛道一、方向一“经贸与校园赋能智能体”设计。原需求的校园门户、教室、教师、地图、点评与课表提供工具底座；核心创新应落在大模型如何利用上下文、调用多个工具并完成具体任务，而不是模块数量。

比赛通知要求使用大语言模型、知识库、工具调用与工作流编排，并通过典型任务验证。当前按项目方选择先交付离线规则演示版，不能据此声称已经满足大模型智能体要求。模型适配入口已实现，正式提交前需要接入并完成真实模型任务测试。

## 建议新增与修正

1. **智能体任务链**：用户描述需求 → 参数提取/澄清 → 查询空闲教室 → 路径规划 → 给出结果与页面入口。展示真实工具返回与来源，避免只生成一段聊天回答。
2. **可信知识**：每条信息记录出处；示例与真实导入数据标明来源。未知政策不回答成确定事实。后续将官方办事指南拆分为知识条目，保留标题、发布日期、链接和有效期。
3. **个性化上下文**：仅在用户主动勾选时上传当前学期本地课表。后续加入按周次、节次计算空档的工具，由代码计算约束，模型负责解释。
4. **评测与对比**：用相同任务比较纯问答、规则工具和大模型工具三种方式。记录成功率、参数正确率、工具调用次数、耗时、错误与澄清情况；当前不编造指标。
5. **隐私与点评治理**：邮箱未经验证，无法证明校内身份；使用 HMAC 摘要做限次，管理凭证做删除权限。前台不公开邮箱，所有文字经人工审核再发布。生产环境需增加经验证的身份、持久限流和更完善的内容审核。
6. **一致性修正**：教室与课表统一 1–14 节；演示中的“博学楼”改为当前目录已有的学思楼；不捏造成绩单等业务深链接，只保留已提供的办事大厅地址。
7. **无障碍与地图精度**：地图坐标为示意，距离及设施不作为实际指引；无障碍路线需要门禁、坡道、楼层和入口实测后才能承诺可通行。

## 首期实现范围

已包含：服务首页、全站搜索、规则助手及可选模型工具循环、45 间示例教室的占用筛选与楼层视图、教师信息搜索及纠错、低模 3D 场景和 Dijkstra 路线、点评提交/限次/验证码/审核/举报/统计、本地课表增删改与冲突检测、JSON 和简单 CSV 导入导出、公告校历、收藏反馈、后台 CSV 导入。

SQLite 用于无外部服务的本地演示；Docker 配置采用 PostgreSQL。界面用 React/TypeScript、定制 CSS 和 Lucide 图标，地图使用 Three.js；为首期简化，没有引入 Ant Design、Zustand、ECharts、Redis。

尚未实现：学校 SSO、实时教室接口、官网教师自动爬取、实际地图校准、Excel/图片课表识别、课表拖拽、账户同步、点赞与排行、点评编辑、公告编辑删除、后台地图编辑、多模态输入。这些功能不应在申报或演示中标为已完成。

## 参赛前优先级

- P0：接入真实模型，补充参数缺失时的澄清测试、模型调用失败测试、提示注入测试；使用 20–30 个真实任务记录效果。
- P0：获取一份获准使用的教室占用和课程数据，导入时替换对应示例条目，校核教室/地图编号。
- P1：官网公开教师信息人工核验后导入；地图优先实测图书馆、教学楼、餐厅三个演示点及入口。
- P1：完成有明确权限的审核流程和公开发布环境的安全加固，再考虑真实用户试用。
- P2：语音或课表截图识别、活动推荐、学校单点登录。

建议视频主线：介绍一个学生自习场景 → 助手查询教室并规划路线 → 展开工具轨迹 → 展示课表冲突检测 → 展示点评审核闭环 → 说明示例数据和待接入内容。团队贡献须按实际填写。
